# 🗄️ Archive and Legacy

The active public family lives under the canonical paths in [🗂️ registry](../registry/PUBLIC_PORTABLES.md).

Historical and superseded material should be preserved through Git history or an explicit archive path when that preservation adds retrieval value. It should not remain an accidental competing authority.

## Legacy successor contract

A superseded artifact may remain historically retrievable without remaining current authority. Mark it as legacy, name the active successor, route current-use questions to that successor and reserve the preserved body for historical, provenance or recovery use.

When a stable legacy path or body has material retrieval value, prefer a frozen artifact named:

~~~text
<original-stem>__legacy__YYYY-MM-DD.md
~~~

Include the supersession date, successor, reason, preservation purpose and recovery reference in the artifact's metadata or opening marker. Do not apply new semantic patches to the frozen body. Routing or custody metadata may be repaired only to keep the successor and recovery information accurate.

Use Git history alone when recovery is sufficient and no stable old path is needed. Use an explicit archive when a retained path, historical decision set, lineage value or visible successor pointer materially improves retrieval. Do not copy every old file into archive by ritual.

For the complete operation, lifecycle and metadata contract, use [Source Operations](../docs/SOURCE_OPERATIONS.md).

The branded website may retain legacy download URLs for compatibility. Those URLs are convenience mirrors, not the source of current semantics.

For active public methods, use [🧭 Procedural Projection](../docs/PROCEDURAL_PROJECTION.md), [🧹 Source Hygiene](../docs/SOURCE_HYGIENE.md) and [🧬 Credits & Attribution Ops](../docs/CREDITS_ATTRIBUTION_OPS.md). Archive material remains historical lineage; it does not become current authority merely because it is linked.
