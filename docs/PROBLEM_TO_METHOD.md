# Find the Moon Source method for your problem

This is a **reader's route**, not a new capability, second registry or replacement for canonical methods. Start with a situation you recognize, try the smallest move, and inspect the result. Each entry below points to the existing authority. No app, LLM, memory, tool, connector or external permission is installed by reading it.

**How to use:** open the linked canonical body in an AI with actual retrieval access (or paste/attach its text). Supply only authorized context. Ask for the first move described here and verify the resulting artifact or decision. If you are developing a product, translate the method into your own tested workflow and access controls.

## Find a fit among the 16 current public capabilities

The situations are fictional examples, not real clients or claims of measured results. You usually need **one** method, not all sixteen.

<!-- problem-route: preflight -->
### Preflight

**Concrete problem:** A request contains corrections, context and several possible deliverables.

**First move:** Restate the intended outcome, what must be preserved and what needs approval before acting.

**What to inspect:** One faithful task brief and any consequential unanswered question.

**Stop line:** It does not guess hidden intent or authorize execution.

**Canonical authority:** [Preflight](../portables/preflight/PREFLIGHT.md)

<!-- problem-route: moon-source-setup -->
### Setup

**Concrete problem:** The same project decisions must be repeated in every new AI conversation.

**First move:** Identify a small project context, its governing source and when to update it.

**What to inspect:** A minimal context setup, ownership, update trigger and first test.

**Stop line:** It does not install memory or make every personal detail persistent.

**Canonical authority:** [Setup](../portables/setup/MOON_SOURCE_SETUP.md)

<!-- problem-route: connected-sources -->
### Connected Sources

**Concrete problem:** An AI found a policy document, but you do not know if it is the current approved one.

**First move:** Check actual connector reach, source authority, last revision and read scope.

**What to inspect:** A source reference with freshness and access limitations, or a truthful fallback.

**Stop line:** Reachability is not authorization, completeness or write permission.

**Canonical authority:** [Connected Sources](CONNECTED_SOURCES.md)

<!-- problem-route: source-hygiene -->
### Source Hygiene

**Concrete problem:** Several project files give different answers and an old summary still appears current.

**First move:** Audit stale authority, duplication, conflicting claims and missing owners before editing.

**What to inspect:** A bounded diagnosis with the smallest proposed correction and its owner.

**Stop line:** It is not an automatic corpus repair or a substitute for source review.

**Canonical authority:** [Source Hygiene](SOURCE_HYGIENE.md)

<!-- problem-route: semantic-reweave -->
### Semantic Reweave

**Concrete problem:** A long-running repository has folders inherited from earlier work that no longer match its responsibilities.

**First move:** Temporarily ignore folder names and regroup content by meaning, function and governing authority.

**What to inspect:** A proposed current/latent topology comparison and only the justified moves.

**Stop line:** A new folder structure is not automatically better or authorized.

**Canonical authority:** [Semantic Reweave](SEMANTIC_REWEAVE.md)

<!-- problem-route: source-operations -->
### Source Operations

**Concrete problem:** A meeting changed a real decision, but nobody knows whether to summarize it or update the source of truth.

**First move:** Classify the operation as retrieve, process, metabolize or promote; seek authority before mutation.

**What to inspect:** Either a working interpretation, a minimal sovereign patch with readback, or no change.

**Stop line:** Processing alone never silently writes; novel ideas do not become public methods by naming them.

**Canonical authority:** [Source Operations](SOURCE_OPERATIONS.md)

<!-- problem-route: moon-source-language -->
### Moon Source Language

**Concrete problem:** A project handoff between teams loses source references, exceptions and uncertainty.

**First move:** Specify the recipient, governing source, what meaning must travel and what must stay out.

**What to inspect:** A bounded handoff with provenance, claims and a recipient-facing readback.

**Stop line:** A structured packet does not transfer permission or execute the handoff.

**Canonical authority:** [Moon Source Language](../portables/msl/MOON_SOURCE_LANGUAGE.md)

<!-- problem-route: lifecycle-workspace-router -->
### Lifecycle Workspace Router

**Concrete problem:** A shared folder contains incoming files, pending reviews and approved work without anyone knowing which is which.

**First move:** Keep source-of-record, lifecycle, assignee, revision and file location as separate dimensions.

**What to inspect:** An intake/action/status view pointing to the original source with a verifiable review state.

**Stop line:** A folder or dashboard position is not proof of approval, authorship or task assignment.

**Canonical authority:** [Lifecycle Workspace Router](LIFECYCLE_WORKSPACE_ROUTER.md)

<!-- problem-route: credits-attribution-ops -->
### Credits & Attribution Ops

**Concrete problem:** A guide is adapted and translated by different contributors, and its origin gets lost.

**First move:** Record identity, author, canonical source, transformations, permissions and disclosure boundary.

**What to inspect:** A compact lineage and attribution record that travels with the derived material.

**Stop line:** Recording credit does not establish ownership or grant a missing license.

**Canonical authority:** [Credits & Attribution Ops](CREDITS_ATTRIBUTION_OPS.md)

<!-- problem-route: procedural-projection -->
### Procedural Projection

**Concrete problem:** A team repeats a useful review checklist differently in every project.

**First move:** Extract the stable trigger, sequence, stop line, output and QA, leaving live facts in their sources.

**What to inspect:** A reusable procedure or skill specification that references the governing source.

**Stop line:** Documentation is not an installed skill or proof that the procedure will execute.

**Canonical authority:** [Procedural Projection](PROCEDURAL_PROJECTION.md)

<!-- problem-route: operational-devices -->
### Operational Devices

**Concrete problem:** A recurring review must run in a specific browser or workflow with visible checkpoints.

**First move:** Define the concrete surface, trigger, inputs, authorization, dry-run, stop conditions and receipt.

**What to inspect:** A bounded device contract and evidence of what actually ran on that surface.

**Stop line:** The contract does not provide the browser runtime or unrestricted tools.

**Canonical authority:** [Operational Devices](OPERATIONAL_DEVICES.md)

<!-- problem-route: operational-reliability -->
### Operational Reliability

**Concrete problem:** A deployment or data update fails halfway and retries keep hiding the actual failure.

**First move:** Check target, instrument, dependencies and scope before the smallest reversible retry.

**What to inspect:** A diagnosis, bounded action, before/after receipt and recovery path.

**Stop line:** A new error or tool log does not by itself prove success.

**Canonical authority:** [Operational Reliability](OPERATIONAL_RELIABILITY.md)

<!-- problem-route: failure-foundry -->
### Failure Foundry

**Concrete problem:** The same handoff mistake keeps resurfacing after individual fixes.

**First move:** Collect safe evidence, isolate failure domain, fix the case and test a transferable micro-rule.

**What to inspect:** A tested checklist, gate or procedure candidate, or a situated lesson only.

**Stop line:** One failure does not automatically justify a universal new capability.

**Canonical authority:** [Failure Foundry](FAILURE_FOUNDRY.md)

<!-- problem-route: signal-calibration -->
### Signal Calibration

**Concrete problem:** Several weak indicators suggest a project is slipping, but no single signal proves it.

**First move:** Separate observations, dependent cues, leading inference, meaningful alternative and update condition.

**What to inspect:** A working interpretation with explicit evidentiary floor and uncertainty.

**Stop line:** Plausible inference is not a verified fact, diagnosis or probability score.

**Canonical authority:** [Signal Calibration](SIGNAL_CALIBRATION.md)

<!-- problem-route: be-my-eyes -->
### Be My Eyes

**Concrete problem:** A reply from a colleague sounds ambiguous and you want to answer without overreacting.

**First move:** Read the interaction as a scene: observation, relationship, possible reception and overread.

**What to inspect:** A proportionate response posture grounded in what is known.

**Stop line:** It cannot reveal the colleague's motive or guarantee their reaction.

**Canonical authority:** [Be My Eyes](../portables/be-my-eyes/BE_MY_EYES.md)

<!-- problem-route: adaptive-orchestration -->
### Adaptive Orchestration Protocol

**Concrete problem:** A large task wastes expensive reasoning on repetitive extraction and repeats the same context across handoffs.

**First move:** Separate the decision bottleneck from bulk work; choose available surface, model effort and delegation proportionally.

**What to inspect:** An execution plan with acceptance checks and total-work tradeoffs.

**Stop line:** It does not unlock unavailable models, agents, budgets or execution rights.

**Canonical authority:** [Adaptive Orchestration Protocol](../portables/adaptive-orchestration/ADAPTIVE_ORCHESTRATION_PROTOCOL.md)

## Compositions for real project shapes

These are **invented examples** showing when a second method earns its place. The method names are not a compulsory pipeline.

### A learning program spanning several sessions

The person returns after a break and the operational module has changed. Start with [Conversational Context](CONVERSATIONAL_CONTEXT.md) to select only the approved purpose-bound state, compare the authorized earlier step with the current program record and distinguish a human-review recommendation from an actual delivered referral. Bring in [Connected Sources](CONNECTED_SOURCES.md) only if the host can access a legitimate current system. If a durable project setup is also needed, use [Setup](../portables/setup/MOON_SOURCE_SETUP.md). **Inspect:** the current approved step, excluded old fields, uncertainty and unsent handoff status. No explanation for the absence is inferred.

### A volunteer team whose responsibility shifts

A submission reaches a shared folder but no reviewer has accepted it. Use [Lifecycle Workspace Router](LIFECYCLE_WORKSPACE_ROUTER.md) for source-of-record, lifecycle, action and revision; [Source Operations](SOURCE_OPERATIONS.md) enters only for an authorized update. Use [Credits & Attribution Ops](CREDITS_ATTRIBUTION_OPS.md) only if the submitted document has material origin or reuse concerns. **Inspect:** one source pointer, an explicit assigned action, and a verified revision-bound review stamp. Folder location alone is not approval.

### A knowledge base gives conflicting answers

A fresh API note and an older guide disagree. Start with [Source Hygiene](SOURCE_HYGIENE.md) to identify stale authority and duplication. Use [Semantic Reweave](SEMANTIC_REWEAVE.md) only if the corpus's *structure* itself is wrong, not merely one outdated paragraph. If a patch is authorized, use [Source Operations](SOURCE_OPERATIONS.md) with readback; repeated failure may justify [Failure Foundry](FAILURE_FOUNDRY.md). **Inspect:** the authoritative fact, the minimal change, and whether an actual readback occurred.

## How to tell if the method helped

Before expanding to a second module, check: *Did we make a material distinction that was missing? Can another person inspect the outcome? Does it still point to its governing source? Do we know what has not been executed or proved?* If nothing changed, prefer plain language and existing project tools.

For app-specific implementations, see [For AI Builders](FOR_AI_BUILDERS.md) and [From Method to Implementation](FROM_METHOD_TO_IMPLEMENTATION.md). The [Evidence and Claims](../EVIDENCE_AND_CLAIMS.md) boundary applies to every illustrative example. In particular, a described workflow is not a deployed integration.
