# Failure to Capability — Failure Foundry

Failure Foundry is a bounded loop for turning a recurring, costly, systemic or epistemically dangerous failure into the smallest reusable capability that has actually earned publication or reuse.

It treats failure as evidence to be classified and metabolized. It does not treat every error as doctrine, and it does not claim autonomous self-improvement.

## Public loop

```text
repeated or costly failure
  → preserve evidence
  → separate failure domains
  → identify the missed layer or clue
  → solve or safely escalate the current case
  → classify situated vs transferable learning
  → forge the smallest useful artifact
  → validate the artifact
  → update the smallest authoritative source
```

The loop is a decision aid, not a license to expose the case that revealed the learning.

## Run the loop

### 1. Detect a real pattern

Look for recurrence, avoidable cost, repeated operator confusion, a dangerous misclassification, a missing stop line or a failure that keeps defeating the same strategy. One strange event may be important, but it does not automatically earn a general rule.

### 2. Stop repeating the same strategy without new evidence

If the same intervention produces the same state, pause. Preserve the prior attempts, their actual outputs and the assumptions they depended on. Do not call persistence “resilience” when it is only repetition without learning.

### 3. Preserve useful evidence

Keep the smallest safe record of:

- what was requested;
- what was observed;
- what was attempted;
- which layer was assumed;
- what changed or stayed the same;
- what was missing, partial or misleading;
- which privacy, security, custody or disclosure boundary applied.

The public record should preserve the mechanism, not private names, local state, account details, credentials or a reconstructable case corpus.

### 4. Separate failure domains

Ask whether the failure belonged to the `TARGET`, `INSTRUMENT`, `ENVIRONMENT`, `DEPENDENCY`, `INSTRUCTION`, `INTERACTION`, `OPTIONAL_PROBE` or `UPSTREAM_SERVICE`. A broken instrument should not produce a target-blame rule. An optional probe should not invalidate a valid core result. A changed upstream service should not be fossilized as a permanent local diagnosis.

Use [Operational Reliability](OPERATIONAL_RELIABILITY.md) for the public failure-domain and receipt contract.

### 5. Find the missed clue or layer

Name what the previous strategy could not see:

- a dependency was never proven;
- the runtime or session was absent;
- the diagnostic script never started;
- a reference pointed to a non-existent object;
- a partial result was misread as failure;
- a new error was misread as regression or success;
- a guardrail or authorization boundary was missing;
- a stale external assumption survived past its freshness window.

This step should change the next operation. If it changes nothing, the explanation may be narrative rather than capability.

### 6. Solve or safely escalate the current case

The current target still matters. Apply the smallest safe repair, resume from trustworthy state, quarantine an isolated item, restore a reversible change or escalate with an evidence-bearing handoff. Do not use the promise of future learning as a reason to leave the present failure unmanaged.

### 7. Classify the learning

Decide whether the learning is:

| Class | Meaning |
|---|---|
| Situated | Useful for this target, surface, relationship, environment or moment only |
| Transferable | Likely to help across more than one comparable field, with boundaries still visible |
| Candidate public pattern | Transferable enough to state as a responsibility, interface, guard, template or bounded example |
| Reserved | Useful, but disclosing it would expose private machinery, security, personal material or a protected source boundary |

Transferability is not the same as universality. A pattern may travel while still requiring a named adapter, domain method or freshness check.

### 8. Forge the smallest useful artifact

Choose the form that changes future capability:

| If the learning changes... | Consider... |
|---|---|
| one decision or interpretation | a micro-rule or checklist |
| acceptance or rejection | a QA check or gate |
| repeated human wording | a template or handoff field |
| diagnosis | a diagnostic or failure-domain record |
| a repeatable sequence | a procedure or protocol |
| a stable method that needs transport | a procedural projection |
| bounded execution on a concrete surface | an operational device |
| a governed fact, decision or current state | an authoritative source patch |

Do not create a new component when a source patch or small QA rule is enough. Do not create a device when there is no concrete surface or bounded output.

### 9. Validate before promotion

Use readback, self-test, dry-run, regression evidence, synthetic fixtures, a bounded implementation test or an equivalent inspection. Validation should show that the artifact changes the relevant behavior or makes the failure legible.

The public surface may name qualitative factors such as recurrence, cost, risk, transferability, changed protocol and validated reuse. It must not publish private numeric promotion thresholds, hidden evaluation corpora, compiler ordering or mutation machinery.

### 10. Update the right source

Write to the smallest authoritative public or private source that owns the delta. A changelog records the release; it does not become the governing method. A demo proves a bounded slice; it does not replace the component contract. An archive preserves lineage; it does not silently govern current behavior.

Record claim ceiling, freshness, public/private boundary and lineage when those facts affect later use.

## Anti-patterns

- a “version 4” that only repackages the same broken topology;
- blaming the target when the instrument never started;
- turning every transient error into a protocol;
- keeping a museum of errors instead of extracting capability;
- declaring systemic learning without a changed rule, gate, template or procedure;
- publishing private promotion thresholds as universal doctrine;
- calling a synthetic fixture external adoption;
- treating a public implementation as permission to publish private adapters or credentials;
- using a new component to avoid repairing the authoritative source.

## Public boundary

This component may publish the failure-to-capability loop, qualitative selection factors, public-safe failure domains, bounded examples and claim discipline.

It must not publish:

- private case narratives, personal or third-party material, machine state or credentials;
- private adapters, selectors, endpoints, corpora or account/session data;
- exact promotion thresholds, hidden weights, evaluation corpora, compiler logic or source mutation ordering;
- enough cross-file detail to reconstruct protected machinery;
- a claim that the repository contains an autonomous self-improvement engine.

## Review prompt

```text
Run a bounded Failure Foundry review on the material below.

Return:
1. repeated or costly failure signal;
2. evidence preserved;
3. failure domains separated;
4. missed layer or clue;
5. current-case repair or safe escalation;
6. situated vs transferable learning;
7. smallest artifact that earns existence;
8. validation and readback;
9. authoritative source to update;
10. claim ceiling, freshness and public/private boundary.

Do not expose private promotion machinery, hidden thresholds, credentials or source-specific details that are not necessary for the public capability.
```

## Claim ceiling

This is a bounded public projection of a failure-to-capability method, internally informed by repeated operational failures. It is not an autonomous self-improvement engine, compiler, benchmark, universal standard or evidence of measured impact. It does not make private cases public merely because they produced a reusable insight.

Use [Operational Reliability](OPERATIONAL_RELIABILITY.md) for execution evidence and recovery, [Operational Devices](OPERATIONAL_DEVICES.md) for bounded embodiment, and [Procedural Projection](PROCEDURAL_PROJECTION.md) when the resulting method needs a portable procedural surface.

See [Evidence and Claims](../EVIDENCE_AND_CLAIMS.md) and [Public Boundary](../PUBLIC_BOUNDARY.md) for the public evidence and disclosure limits.
