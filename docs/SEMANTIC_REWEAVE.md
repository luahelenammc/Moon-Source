# 🧵 Semantic Reweave — Moon Source component

A bounded method for recovering the latent semantic topology of an evolving project or corpus and repairing inherited organization without rebuilding it from scratch.

> **Let meaning regroup before containers govern it.**

## Function

Use Semantic Reweave when a project has accumulated enough themes, models, observations, cases, procedures, conclusions or artifacts that its inherited organization may no longer represent the structure of the material itself.

The method does not begin by asking which file should be renamed, split or created. It begins one level earlier: **which things actually belong together, which things are only co-located by historical accident, which things were separated despite sharing one responsibility, and which relationships have never been made explicit?**

Its goal is not novelty. Its goal is a more truthful and usable topology with the smallest justified structural mutation.

**MSL profile:** 5.1-compatible Markdown-native method surface; preserve semantic responsibility, authority, provenance and source-of-record boundaries while changing form only when the field earns it.

## The structural problem

Long-lived projects rarely become incoherent all at once. More often they grow by local success:

- a useful file receives one more adjacent responsibility;
- a temporary section becomes a permanent home;
- two different concepts inherit the same label;
- the same concept develops in several places;
- a new theme appears but remains scattered because no container was created for it;
- a historical location keeps semantic authority after a better source has emerged;
- an organizational choice that once made sense becomes the reason unrelated material keeps being interpreted together.

This produces **container inertia**: the existing map starts shaping the meaning of the territory.

Semantic Reweave reverses that dependency. The current containers remain evidence about the project's history, but they are not assumed to be the correct ontology of the present.

## Core principle

> **Temporarily distrust the containers, recover the latent semantic topology, compare it with the inherited topology, then repair only the material mismatch.**

This creates three distinct objects:

1. **Current topology** — where material is presently stored, named, linked and treated as authoritative.
2. **Latent topology** — the grouping and relationship pattern that emerges from the material's actual meaning, function, evidence base, update cycle and consequence.
3. **Reweave delta** — only the differences important enough to justify a structural repair.

The latent topology is not automatically correct merely because it is newly inferred. It is a working structural model that must survive authority, provenance and consequence checks before it changes the project.

## Semantic units before containers

Start by identifying the units that the project is actually made of. Depending on the field, these may include:

- themes and concepts;
- observations and raw evidence;
- interpretations and working models;
- cases and instances;
- procedures and operational rules;
- decisions and conclusions;
- actors, roles and relationships;
- artifacts, sources and records;
- unresolved questions;
- historical material and provenance;
- interfaces, bridges and routing rules.

Do not force every unit into one ontology. A case, a model, a source and a procedure can discuss the same subject while owning different responsibilities.

## Container Erasure Test

The central diagnostic is the **Container Erasure Test**. A practical file-based form is the **Filename Erasure Test**.

Temporarily ignore file names, folder names, numbering, section headings and inherited category labels. Then ask:

> **If these containers had never existed, which pieces of material would still want to stay together, and why?**

Recover candidate groupings using several kinds of affinity rather than keyword similarity alone:

- **semantic affinity** — they describe the same phenomenon or conceptual object;
- **functional affinity** — they perform the same job;
- **evidentiary affinity** — they depend on the same evidence class or epistemic status;
- **authority affinity** — they belong under the same governing source or responsibility;
- **update affinity** — they change for the same reasons and at roughly the same lifecycle;
- **consequence affinity** — errors or decisions in them propagate through the same downstream field;
- **relational affinity** — understanding one materially changes the interpretation of the other.

A strong cluster usually survives more than one of these tests. Mere topical resemblance is not enough.

## Reweave classification

Compare the latent topology with the current topology and classify only material mismatches.

| Classification | Meaning |
|---|---|
| **coherent cluster** | Material is grouped together for a defensible shared responsibility. Preserve it. |
| **forced cohabitation** | Different responsibilities share a container mainly because history placed them there. |
| **false split** | One semantic or operational responsibility is fragmented across containers without a useful jurisdictional reason. |
| **missing cluster** | A real recurring grouping exists in the material but has no visible home, hub or organizing relation. |
| **duplicate shadow** | A concept is repeated in several places and the copies ambiguously compete for authority. |
| **jurisdiction leak** | Material has crossed into a container whose responsibility should not govern it. |
| **orphan** | Material matters but has no clear relationship, owner, destination or lifecycle. |
| **premature abstraction** | A general model was created before enough grounded material justified it, causing the model to organize evidence too early. |
| **missing bridge** | Two correctly separate responsibilities materially depend on each other but the relation is not represented. |
| **source-of-record confusion** | Several surfaces appear to govern the same current truth, or the historical location still behaves as authority after succession. |

The taxonomy is diagnostic, not decorative. Do not assign a label unless it changes what should be preserved, connected, moved, split, merged, deprecated or clarified.

## Authority before movement

Semantic closeness does not automatically justify physical consolidation.

Before changing containers, resolve:

1. What responsibility does each cluster actually own?
2. Which source, artifact or role is the current source of record for that responsibility?
3. Which repetitions are deliberate projections, summaries, indexes or historical provenance rather than competing authorities?
4. Which boundaries exist for privacy, audience, lifecycle, legal meaning, execution or update cadence?
5. Would moving the material simplify understanding while making authority harder to recover?

Two things may be semantically close and still need separate homes. The repair may be a bridge rather than a merge.

## Least-mutation repair ladder

Apply the smallest repair that makes the semantic topology legible and authoritative.

Prefer this order unless the field gives a concrete reason to escalate:

1. **Clarify authority.** Declare the source of record, jurisdiction or succession relation.
2. **Add a bridge, hub or index.** Make a real relationship visible without relocating correct sources.
3. **Add a migration or deprecation note.** Preserve provenance while ending false current authority.
4. **Rename or narrow a container.** Correct a misleading label when the underlying material is mostly well placed.
5. **Move a bounded block.** Relocate material whose current home is materially wrong.
6. **Split or merge containers.** Use only when responsibilities themselves are structurally misrepresented.
7. **Create or remove an artifact.** Treat this as the highest-cost ordinary repair, not the default proof that analysis happened.

The ladder is not a rigid waterfall. A clear source-of-record collision may require direct movement. Its purpose is to resist architectural theatre: large structural change should carry a larger burden of proof.

## Provenance preservation

Reorganization must not erase how the project learned what it knows.

When material moves or authority changes:

- preserve enough lineage to recover the prior location when that history matters;
- distinguish current authority from historical provenance;
- keep observations distinguishable from later interpretation;
- avoid rewriting old records merely to make the present architecture look cleaner;
- use succession, redirect or migration notes when old paths may still be referenced;
- do not create a second canonical copy while trying to make a first one easier to find.

A cleaner tree with broken lineage is not a successful reweave.

## Public execution loop

Use only the depth the project requires.

1. **Set the scope.** Identify the project/corpus and whether the operation is diagnosis-only or authorized to mutate structure.
2. **Inventory semantic units.** Read broadly enough to see recurring meanings, responsibilities, evidence classes, actors, decisions and update cycles.
3. **Run container erasure.** Derive candidate clusters without letting current names decide the result.
4. **Recover relationships.** Identify bridges, dependencies, succession and source-of-record relations between clusters.
5. **Compare topologies.** Mark coherent clusters and material mismatches using the reweave classification.
6. **Resolve authority.** Determine which surface should govern each current responsibility before moving content.
7. **Design the smallest reweave delta.** Prefer authority clarification, bridges and hubs before large-scale relocation.
8. **Apply only authorized mutations.** Preserve provenance and avoid opportunistic cleanup outside the accepted delta.
9. **Read back the resulting topology.** Verify names, paths, authority pointers, links and absence of accidental duplicate authority.
10. **Stop when legibility is restored.** Do not continue reorganizing merely because more rearrangements are imaginable.

## Output contract

A useful Semantic Reweave result should make visible, proportionately:

- the strongest coherent clusters already worth preserving;
- forced cohabitations or false splits that materially distort understanding;
- missing clusters or bridges;
- authority and source-of-record conflicts;
- the proposed target topology;
- the smallest concrete reweave delta;
- what remains deliberately unchanged;
- provenance or migration requirements;
- whether structural mutation was actually performed and read back.

A valid result can be **no structural change** when the inherited topology survives the test.

## Synthetic example

A long-running research project has four files: `cases.md`, `models.md`, `community.md` and `notes.md`.

Over time:

- `community.md` begins storing both broad community observations and detailed profiles of individual collaborators;
- raw interview excerpts accumulate beside conclusions in `models.md`;
- one recurring concept appears in all four files under slightly different names;
- `cases.md` still contains an early framework that was later refined in `models.md`.

A superficial cleanup might create more folders. Semantic Reweave instead finds:

- community-level ecology and individual collaborator records are a **forced cohabitation**;
- raw excerpts inside `models.md` are a **jurisdiction leak** if evidence belongs in case/source records;
- the recurring concept is a **missing cluster** or **missing bridge**, depending on whether it needs a sovereign home or only a cross-project hub;
- the old framework is a **duplicate shadow** if readers can still mistake it for current authority.

The smallest repair may be to narrow `community.md`, establish a collaborator source of record, route evidence back to the case layer, create one conceptual hub in `models.md`, and leave historical copies in place with explicit succession notes. No fifth file is required unless the recovered responsibility actually earns one.

This example is synthetic and does not report a real project, organization, adoption or measured outcome.

## 🛠️ Apply it now

Copy this bounded worksheet into an AI conversation:

~~~text
Run Moon Source Semantic Reweave on the project or corpus below.

Goal:
Recover the latent semantic topology of the material and compare it with the inherited organization. Do not redesign from scratch.

Perform:
1. inventory the meaningful units, responsibilities and current sources of record;
2. run the Container Erasure Test / Filename Erasure Test;
3. identify coherent clusters worth preserving;
4. classify only material mismatches as forced cohabitation, false split, missing cluster, duplicate shadow, jurisdiction leak, orphan, premature abstraction, missing bridge or source-of-record confusion;
5. distinguish semantic closeness from jurisdictional authority;
6. propose the smallest reweave delta using the least-mutation repair ladder;
7. preserve provenance and historical lineage;
8. if mutation is authorized, apply only the accepted structural delta and read back the resulting state.

Prefer clarification, bridges, hubs and source-of-record repair before moving, splitting, merging or creating artifacts.
A valid result may be no structural change.
Do not manufacture a new taxonomy merely to make the output look novel.

Project / corpus:
[attach, link or describe the governed material]
~~~

## Relationship to adjacent Moon Source capabilities

Semantic Reweave owns **semantic-topology reconstruction and repair**. Adjacent capabilities keep their own responsibilities:

- [Source Hygiene](SOURCE_HYGIENE.md) diagnoses authority, freshness, duplication, contradiction, orphaned decisions, provenance and bounded corpus repair. It can reveal that a corpus is unhealthy; Semantic Reweave asks whether the project's conceptual and responsibility groupings themselves are misdrawn.
- [Responsibility Map](RESPONSIBILITY_MAP.md) separates ownership, authority and transport between objects. Semantic Reweave may call it when a recovered cluster exposes an ownership or jurisdiction collision.
- [Field to Form](../ARCHITECTURE.md#field-to-form) decides what should exist before choosing a container. Semantic Reweave often runs earlier on an already-grown project, then uses Field to Form only if the recovered topology earns a new or changed artifact.
- [Moon Source Language](../portables/msl/MOON_SOURCE_LANGUAGE.md) can materialize an accepted topology while preserving semantic passage, authority and boundaries. MSL does not decide that a reorganization is needed merely because it can express one.
- [Source Operations](SOURCE_OPERATIONS.md) governs retrieve, process, metabolize and promote operations across sources. Semantic Reweave can produce a structural delta; Source Operations governs source mutation when that delta crosses source jurisdictions.

Do not collapse these into one universal architecture engine. Their value comes partly from keeping diagnosis, topology, responsibility, form and source mutation distinguishable.

## Failure modes and QA

Check for:

- **container obedience** — reproducing the current grouping because filenames already suggested it;
- **topic-only clustering** — merging things that mention the same subject but own different responsibilities;
- **architecture theatre** — creating new files, folders or taxonomies mainly to demonstrate that reorganization occurred;
- **over-splitting** — giving every detectable theme its own container;
- **over-merging** — treating semantic affinity as sufficient reason to erase useful jurisdictional boundaries;
- **authority cloning** — creating a second current source of record while trying to improve discoverability;
- **provenance amnesia** — deleting or rewriting history so the new structure appears cleaner;
- **rename-only repair** — changing labels while leaving the same confused responsibility underneath;
- **premature ontology** — forcing the whole project into a new conceptual system before the latent topology is well supported;
- **cleanup creep** — expanding an accepted reweave into unrelated formatting, rewriting or archival work;
- **novelty pressure** — treating `no structural change` as failure.

Ask:

1. If the filenames and headings disappeared, would the proposed clusters still emerge?
2. Does each proposed cluster share a real responsibility, not merely a topic?
3. Is there one clear current source of record for every material responsibility?
4. Could a bridge solve the problem more safely than a move or merge?
5. Does the proposed change preserve provenance and historical recoverability?
6. Is every new artifact justified by a responsibility that cannot be represented more cheaply?
7. After the reweave, can a new reader understand both **what belongs together** and **who governs what**?

## Claim ceiling

Semantic Reweave is a bounded public semantic-topology and corpus-reorganization method. It is:

- not an autonomous refactoring or migration engine;
- not proof that a recovered cluster is an objectively true ontology;
- not a universal taxonomy or knowledge representation standard;
- not permission to mutate governed sources without authority;
- not a guarantee that fewer files, more files or a particular hierarchy is better;
- not a substitute for domain-specific evidence, records management, legal retention or safety requirements;
- not evidence of external adoption, measured productivity gain or validated superiority.

See [Architecture](../ARCHITECTURE.md), [Evidence and Claims](../EVIDENCE_AND_CLAIMS.md), [Public Boundary](../PUBLIC_BOUNDARY.md) and [Existing Implementations](EXISTING_IMPLEMENTATIONS.md) for the surrounding authority and disclosure boundary.
