## 1. What changed, and what did not

OpenAI introduced **GPT-6.1 Terra** on 2026-10-26 as a fast, comparatively inexpensive model for visually grounded professional execution. Relative to GPT-5.6 Terra, OpenAI reports stronger computer-use, visual reasoning, factuality and command-line software engineering. Terra 6.1 is available in **ChatGPT Work and Codex** for eligible Plus, Pro, Enterprise and Edu users, and via the API as `gpt-6.1-terra`. Availability of a model in a product does not prove that any particular workspace, root agent, child-agent selector or task has access to it. Do not label Terra an ordinary Chat model unless that surface actually exposes it.

**Core law unchanged:** maintain the current competent control root; separate root, executor, harness, effort, behavioral fit, commitment authority and verification. Delegate only where the actual environment permits. Terra's release changes *workload-fit calibration*, not the stable AOP tiers or its semantics. This adapter is not a new capability identity or a forced migration to Work.

## 2. Economic geometry (dated API Standard figures)

| Executor | Input / 1M tokens | Cached input / 1M | Output / 1M | Inference |
|---|---:|---:|---:|---|
| GPT-6 Luna | $0.10 | $0.01 | $0.50 | cheaper for simple bulk if sufficient |
| GPT-6.1 Terra | $1.00 | $0.05 | $5.00 | efficient intermediate for screen/vision work |
| GPT-6.1 Sol | $2.00 | $0.10 | $10.00 | stronger complex execution/architecture |
| GPT-6 Astra | $10.00 | $1.00 | $50.00 | frontier when its differential matters |

These are **standard short-context API unit prices**, not ChatGPT Work/Codex credit ratios. Terra's uncached input/output are 50% cheaper than Sol's and 90% cheaper than Astra's, **but 10× more expensive than Luna's**. Cached-input price ratios differ. API calls with different context sizes, caching, tools, retries, reasoning effort or billing modes may cost differently. In Work/Codex, OpenAI says the same usage allowance covers more Terra tasks than GPT-5.6 Terra, Sol 6.1 or Astra; it does **not** establish a precise allowance-to-API-token formula or published Terra-vs-Luna usage ratio.

**Optimize cost *to accepted output*, not the lowest unit price.** Count tool latency, manual reviewer effort, failed actions, retries, replay of a mistaken design commitment, and source re-ingestion. A low per-token price does not justify a weak executor that repeatedly fails acceptance; a high reasoning tier does not justify running routine form entry on Astra.

## 3. Evidence ledger, not a universal ranking

OpenAI's October 26 release reports:
- **Agents' Last Exam:** at medium effort, Terra 6.1 scores about **15 percentage points** above GPT-5.6 Terra at approximately one-third the *cost per task*; near GPT-6 Astra on that reported evaluation at roughly one-tenth the price per token.
- **Time to finish:** more than **3× faster** than GPT-6 Astra and GPT-6.1 Sol in the stated comparison, not guaranteed in every user workflow.
- **MMMU-Pro:** superior to GPT-5.6 Terra across reported reasoning settings and approaches Sol/Astra on visual reasoning.
- **OSWorld 2.1:** at medium effort, surpasses GPT-5.6 Terra's reported best score at lower cost per task.
- **Error-inducing prompts:** reported error rate from 53.6% (5.6 Terra low effort) to 16.7% (6.1 Terra low effort); at maximum effort Terra 6.1 reports 4.3%. This is an internal evaluation, **not** a 4.3% error guarantee for real work.
- **Terminal-Bench 4.0:** at maximum effort, 50.3% for Terra 6.1 versus 21.5% published for GPT-5.6 Terra. Sol/Astra remain the recommended options for the most complex coding.
- **Terminal-Bench-Science 0.1:** Terra 6.1 at max exceeds Sol 6.1 in OpenAI's reported evaluation and approaches Opus 5.5 at lower cost. This is a *specific workload result*, not a general scientific-superiority claim.

These are provider-reported benchmark conditions; effort, tool harness, datasets and date matter. They motivate representative micro-probes when needed, not a permanent model winner. Safety ratings and prompt-injection tests do not supersede human consent, source authority, data minimization, or action-level guardrails.

## 4. Terra-shaped tasks

Prefer a **bounded Terra trial** when the task's capability floor and authorization are satisfied and the material work requires one or more of:

- visual interpretation of app screens, images, diagrams, catalogs or technical drawings;
- accurate stepwise UI actions: navigating menus, entering form data, reconciling invoices and records, performing repeatable office tasks;
- multimodal comparison grounded in screenshots, with visual evidence at each decisive step;
- straightforward professional drafts, revisions and artifact updates that require natural writing;
- scoped code edits and command-line fixes with executable tests and unambiguous acceptance;
- many independent screen-based or visual subtasks for which task throughput, latency and lower replay burden matter.

**Do not conflate seeing with doing.** The model needs a real connected computer-use harness and the task's permissions; it does not acquire browser, desktop, video-editing or file rights merely because an announcement says it can work on those tasks. Analyze visually where possible; perform screen actions only through available authorized tools. For sensitive submissions, financial/medical records or irreversible actions, preserve checkpoints, confirmation when required and readback.

## 5. Decision routing alongside Luna, Sol and Astra

This is an **overlapping fit map, not a compulsory Luna → Terra → Sol → Astra ladder**:

1. **Keep Luna** for bounded text-heavy extraction, batch transformation, straightforward verification and high-volume routine work when it actually passes the capability and behavioral gates. Terra is not the universal cheaper substitute for Luna.
2. **Choose Terra as a strong candidate** for work whose hard part is visual grounding or interacting with software, including multi-step but well-bounded workflows; choose an appropriate effort level and a small representative test when uncertainty matters.
3. **Choose Sol 6.1** when open-ended programming, large refactors, branching operational reasoning, cross-domain architecture or a costly-to-reverse commitment genuinely needs stronger integrative cognition. A complex system decision can remain with Sol while Terra carries screen work.
4. **Choose Astra** when material frontier cognitive/creative judgment, evidence of a task-specific advantage, highest-capability user preference or unacceptable replay risk warrants its premium. Preserve role plurality, including reviewer, co-architect and sustained root when appropriate.
5. **Side-route for Behavioral Fit** when Terra is cognitively sufficient but violates voice, source fidelity, restraint or UI-action reliability; **up-route** only for a diagnosed capability shortfall. Fix tool, access, source, specification or permission failures without blaming the model.
6. **Use Decision Commitment Gate** before multiplying cheap actions behind an unvalidated form mapping, design, data transformation or destination. An inexpensive wrong commitment becomes expensive replay.

When a competent Sol/Astra root exists and the runtime exposes supported heterogenous workers, delegate reducible visual/computer work to Terra; do not manually switch surfaces merely to simulate that delegation. When Terra itself is a competent root, keep it through execution and Control-Root Postflight. If child-model overrides are unavailable, describe the actual fallback, not an imagined spawn.

### Example execution shapes

- **Invoice ingestion:** Luna may normalize already-extracted text; Terra may read onscreen invoices and enter fields; Sol reviews ambiguous accounting mappings or unusually complex exception rules. Human approval still governs financial commitments.
- **3D/game workflow:** Terra may inspect screenshots, log shot-by-shot changes and repair a scoped UI regression. Sol/Astra should handle genuinely unresolved game architecture or high-stakes creative direction when evidence supports it. No benchmark here proves equal visual artistry for an entire game.
- **Admin portal:** Terra can navigate and draft entries with a bounded checklist and post-action readback; a submitted legal/medical/financial filing still obeys authorization and confirmation requirements.

## 6. Probe / effort / acceptance discipline

- Start with **medium reasoning effort** when exposed; lower for clear repetitive work, increase only if error/retry reduction justifies it. API supports `none | low | medium | high | xhigh | max`; the ChatGPT UI may expose different controls.
- State the screen/task acceptance criterion, input boundary, action permissions, stop condition and evidence needed.
- Probe one representative item or screen when model fit is uncertain or a wrong mapping will replicate.
- If Terra succeeds, scale the bounded docket. If it fails, classify `tool_access | source | authorization | specification | behavioral_fit | cognition | commitment`.
- Repair only the affected delta; escalate a *decision*, *fit*, or *capability* separately instead of rerunning the entire job.
- Converge at the competent control root with evidence, partial-completion accounting, accurate claims, and a truthful acceptance state.

## 7. Public/local boundary

The **public AOP default** remains profile-dependent and model-neutral; it does not silently enable Maximum Token Economy or a universal Terra-first policy. Any **Local Moon Source preference** may favor Terra for suitable visual/computer-use workloads but must be identified as a *local profile calibration*, not projected back into public core law. Native Personal Skills, Drive Runtime Mirrors and website/package copies have separate verification states: a GitHub commit alone proves none of those projections are synchronized.
